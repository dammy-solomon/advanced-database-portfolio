## Selected case study

**Northgate Open University (NOU)** — a *simulated* open and distance-learning
university. The organisation is fictional and every record in this repository
is synthetically generated. No data from any real institution is used.

NOU runs fully online degree programmes with three intakes a year.
Prospective students apply online or through a walk-in centre, upload
supporting documents, and pay an application fee. An admissions officer
reviews the file and issues or declines an offer. Applicants who accept and
pay the acceptance fee become enrolled learners, are allocated a success
advisor, register for courses, and are contacted periodically through the
semester.

**Users of the database:** admissions officers, registry staff, success
advisors, programme leads, and the reporting team.

**Major data stored:** applicants, applications, supporting documents,
payments, programmes, faculties, cohorts and seat capacity, staff,
enrolments, courses, course registrations and grades, advisor interactions.

**Key operations supported:** recording applications and preventing duplicate
applications to the same intake; moving an application through its status
lifecycle to a decision; verifying documents; accepting an offer, allocating
a seat and recording payment as one atomic unit; enrolling learners and
assigning advisors; course registration; logging advisor contact; and
reporting conversion by officer, channel and cohort.

The same case study is used consistently across all five portfolio
activities.

## Technical reflection

Building all five activities on Northgate Open University showed how design choices made early in schema modelling ripple through every layer of a database system. Denormalising `cohort.seats_taken` in Portfolio 1 simplified reporting queries in Portfolio 2, but immediately created the lost-update race condition I had to solve with `SELECT ... FOR UPDATE` and `SERIALIZABLE` isolation in Portfolio 3. Similarly, moving learner engagement to MongoDB in Portfolio 4 eliminated nine-table joins and reduced WAN round trips to Atlas M0 in Portfolio 5, at the cost of `$unwind` overhead on cross-learner aggregations and the operational complexity of keeping two stores synchronised.

The biggest technical lessons came from verifying assumptions against actual execution plans and concurrency tests rather than relying on theory alone: discovering that PostgreSQL hoisted an uncorrelated `random()` subquery into an `InitPlan`, seeing `SERIALIZABLE` require genuinely overlapping reads before raising SQLSTATE `40001`, and measuring how partitioning speeds up pruned queries (`17.5 ms`) while slowing down unpruned scans (`193.9 ms`).

- A defect was found and corrected during development: the first version of the data generator used `CROSS JOIN LATERAL (SELECT random())` to obtain a per-row value. Because the subquery was uncorrelated, PostgreSQL hoisted it into an InitPlan and evaluated it once for the entire statement, so all 120,000 applications received an identical status. This was caught by checking the status distribution, and fixed by replacing it with a deterministic hash function keyed on each row.
